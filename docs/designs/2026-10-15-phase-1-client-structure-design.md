# SAVAGE 第一阶段：客户端代码结构设计

基于已确认的浅色六屏设计 v0.2 与 PRD v4.1。本轮交付是代码架构设计，不是已创建或运行的应用。用户已确认视觉方向；技术栈为本轮推荐方案。

## Intent Contract

- intent: 让六个核心页面及必要异常状态拥有清晰的组件、数据和行为边界，支持先验证交互，再接入真机能力。
- constraints: 保留暖白/青柠绿的新版视觉；Solo 首日开放；有效扣放时间与墙钟时间分开；系统中断不判用户失败；模拟记录不冒充传感器记录。
- success_criteria: 每页都有组件归属；每种状态有单一事实来源；能说明邀请、计时、恢复、终止与结果的数据流；明确原型和原生接入的替换点。
- risk_level: medium

当前设计不接真实账户、不发布应用、不处理支付；真实鉴权与个人数据接入需要单独设计验证。

## Verification Contract

verify_steps: 对照 PRD 和六屏图人工核对页面映射、异常矩阵、依赖方向与模拟/真实数据隔离；检查文档链接和规定章节。未运行 App 测试，不将设计检查等同实现验证。

未来实现验收分为三个层次：

| 层次 | 验证对象 | 成功信号 |
|---|---|---|
| 纯规则与协议 | 虚拟时钟、恢复边界、终态、版本、重复事件 | 给定相同事件轨迹得到相同结果；不会重复累计 |
| 页面与交互 | 六屏、Solo、邀请、五类异常、可访问性 | 本地演示流程实际响应；360/390/430 宽度和大字体不裁切 |
| 原生与服务端 | 真机传感器、失活、崩溃恢复、离线补传、两机同步 | 按 PRD AC 用例收集真机和接口证据，浏览器通过不能替代 |

测试命令在应用工程建立并选择兼容依赖版本后写入实施计划；本轮不虚构已存在的 npm scripts。

## Governance Contract

- approval_gates: 本轮是已授权的架构文档工作；不新增安装、部署或外部写入。真正接入账户、凭据和商店发布时，依据对应任务授权处理。
- rollback: 保留 PRD 和 v0.1/v0.2 图稿；本轮文档可单独修订，不修改已实现业务（当前尚无业务代码）。
- ownership: 产品规则由 PRD 维护；客户端负责 UI 与本机记录；服务端负责权限和联合战报；QA 分别记录网页、原生、服务端验证证据。

## Scope

| 本阶段纳入 | 后置 |
|---|---|
| 代码目录、组件拆分、路由和状态来源 | 双商店正式发布 |
| 六屏及首次、等待、异常、历史、设置的结构 | 真实登录/邀请服务与推送实现 |
| 模拟会话与平台端口、原生探针边界 | 支付、排行榜、多人房间 |
| 视觉 token、资产管理和测试分层 | 实时 AI、攻击动画、完整运营后台 |

## Decisions

| # | 决定 | 选择 | 取舍 |
|---|---|---|---|
| D1 | 客户端技术路线 | React Native + TypeScript + Expo 开发构建 | React + Vite 适合纯网页但会增加原生 UI 重写；SwiftUI + Compose 能深度适配但首期双份 UI 成本高 |
| D2 | 页面预览 | 同一客户端工程的 Web 演示模式 | 不再另外建 Vite 产品前端；Web 不能验收真实重力挑战 |
| D3 | 路由 | Expo Router，路由文件保持薄层 | 业务逻辑不放在 URL 参数或页面跳转中 |
| D4 | 工程规模 | 单应用仓库，按业务 feature 分目录 | 无第二个实际消费者前不创建 monorepo、通用 packages 或微前端 |
| D5 | 组件 | React Native 基础组件 + 自有设计 token | shadcn/ui 的 Web DOM 组件不直接引入原生客户端 |
| D6 | 会话事实来源 | 真实设备由原生 FocusEngine 负责记录；页面订阅快照 | React 定时器只刷新显示；浏览器演示使用可替换的模拟引擎 |
| D7 | 状态管理 | 组件局部状态 + 小型订阅式会话存储 | 首期不同时引入 Redux、Zustand、XState；以后有证据再增加依赖 |
| D8 | 后端范围 | 先定义 RoomGateway/ReportGateway 合约和假实现 | 本轮不武断绑定 Java、Node、Supabase 或云厂商 |

Expo 官方文档支持跨平台路由、开发构建与 Swift/Kotlin 自定义模块。它们证明扩展路径存在，不证明本产品的计时、耗电和后台边界已经可靠。[开发构建](https://docs.expo.dev/develop/development-builds/introduction/)、[路由](https://docs.expo.dev/router/introduction/)、[原生模块](https://docs.expo.dev/modules/overview/)。

## Surface

**组件与文件：** 详细目录、页面/组件映射、类型职责、数据流和实施顺序见 [客户端架构参考](savage-client-architecture.md)。目录是拟建结构，标注的原生模块在真机探针阶段建立，不用空文件伪装完成。

**接口：** 页面仅调用 application 层用例；业务层通过 FocusEngine、RoomGateway、ReportGateway、HistoryRepository 等端口访问外部能力。客户端不根据朋友在线状态或共享开关自行宣布胜负。

**存储：** 真实本机记录以原生引擎事务日志为准；上传队列与记录一起提交；UI 历史为可重建投影。模拟数据采用独立命名空间和 source 标签，正式服务拒收。

**视觉：** v0.2 的浅色 token 优先于 PRD 较早的深紫默认。熊和手机插画需要独立资产；页面文本、控件和倒计时使用真实组件，不能将六屏截图裁成背景充当页面。

## Risks & Open Questions

- Windows 可做页面预览及 Android 开发；iOS 本地构建需要 macOS/Xcode，或后续配置远程构建和真机。当前没有真机验证证据。
- React Native 共享 UI 不等于传感器跨平台无差异。原生引擎的 Swift/Kotlin 实现须使用同一批规则测试轨迹核对；探针失败时先保留普通 Solo，不扩大重力功能承诺。
- 框架和原生依赖具体版本在初始化时按 Expo 兼容矩阵锁定，不在文档中猜版本。
- 深色专注进入浅色恢复可能刺激眼睛；原型需检查明暗切换，保留恢复页沿用深底的配置能力。
- 当前六屏只覆盖主路径。无搭子、个人先结束、待同步、权限/传感器缺失等状态必须纳入首轮交互原型。
- 当前方案默认先做 Web 演示和原生探针；真实服务器选型在接入阶段确定，不影响页面模块边界。
